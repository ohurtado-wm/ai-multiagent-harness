01 · Why a harness

A capable agent is not a reliable team.

A coding agent on its own is a capable but forgetful contractor. A harness is everything around the model that makes its work repeatable and safe.

Forgets context between sessionsThe repository is the memory: plans with a status header and context injected at session start.
Ignores team conventionsOne rule file (AGENTS.md) for every agent, plus one per folder.
Follows rules only when it remembers themHooks enforce the critical rules mechanically.
Inconsistent outputSkills turn recurring workflows into fixed procedures.
One huge, expensive contextSubagents and teams: narrow roles, own context, cheaper models.
Reviews its own workCodex writes, Claude reviews, a person merges.
"All tests pass", with no proofOne validation entry point (scripts/verify.sh) for agents and CI.
Work and findings get lost in chatGitHub Issues tracks every plan, every deferred finding and the agents' work queue.
★The design goal: a person steps in for decisions (scope, approvals, merges), never for enforcement.

02 · The idea

Two pillars: detail and coordination.

The repository holds the detail; GitHub Issues holds the coordination. Agents read and write both, and neither one duplicates the other.

Repository

The detail

What must be built, and how.

  • AGENTS.md: one set of rules for every agent
  • Plans in docs/plans/ with a status: header
  • Status per area and a generated plan tree
  • Hooks, skills and roles in .claude/

GitHub Issues

The coordination

What exists, who is on it, what closed it.

  • An issue for every plan: epics and sub-issues
  • An issue for every deferred finding
  • PRs close their issues on merge into dev
  • Labeled issues are a queue agents resolve alone

03 · Built on Claude Code

The harness is configuration. Claude Code is the engine.

Every agent runs in its own context window; none of them shares a conversation. Claude Code is what connects them: it loads the same project memory into each one, gives teams a shared task list and a mailbox, runs the hooks on every tool call and keeps memory between sessions.

Project memory

CLAUDE.md and imports

Loaded at the start of every session, subagent and teammate; @imports pull in other files and folder files load when Claude works there.

Harness: CLAUDE.md → @AGENTS.md, one per folder.
Auto memory

Notes Claude keeps itself

A MEMORY.md index Claude writes as it learns; its first lines load each session. It lives on one machine.

Harness: team decisions move to AGENTS.md so every machine sees them.
Skills

Procedures on demand

SKILL.md files triggered by their description or by /name.

Harness: 8 skills, from feature-plan to resolve-issues.
Subagents

Narrow roles, own context

Each with its own tools, model and, optionally, a persistent memory folder; only a summary comes back.

Harness: 7 roles; reviewers limited to Read, Grep, Glob.
Agent teams

Task list and mailbox

Teammates load the project context, claim tasks with dependencies (file-locked) and message each other by name; the lead is told when one goes idle.

Harness: /orchestrate-team and its briefs.
Hooks

Lifecycle events

SessionStart, PreToolUse, TaskCreated, TaskCompleted, TeammateIdle… exit code 2 blocks with feedback.

Harness: 5 hooks, the safety ones fail closed.
Permissions and settings

Versioned settings.json

Allow and deny rules, environment and options shared by the whole team.

Harness: deny protected pushes, 1 h cache, teams flag.
Plugins

Installable extensions

Bundles of skills, agents, hooks and MCP servers, installed from a marketplace.

Harness: the Codex plugin (codex:codex-rescue) that coders delegate to.
/loop

Self-paced loops

Re-runs a prompt or a skill on its own schedule until the work is done.

Harness: /loop /resolve-issues works the issue queue.
!Why the rules live in the repository: Claude Code's auto memory is per machine. Anything the whole team must follow goes into AGENTS.md, which Claude Code loads into every agent on every machine.

Hooks: rules that don't depend on memory

Small Node scripts run before a tool call. Exit code 2 blocks it; the message tells the agent what to do instead. Every hook has unit tests.

git-guardbefore Bash · everyone

Commits or pushes to main/dev, PRs not against dev, merging into main, rm -rf outside build folders, reading .env. Understands quotes, &&, bash -c, cd and git -C.

team-guardsubagents and teammates

Any git history change or PR command, editing the harness config, local database resets, regression tests without the owner's yes.

generated-guardbefore edits

Hand-editing generated files; says which source to edit and which command to run.

task-gatetask created / completed

A plan-block task without a Verification: <command> line.

session-contextsession start

Injects branch, open PR, touched plans and active plans, written as facts.

FAIL CLOSEDSafety hooks run with onFailure: "block" and timeout: 30: a crashed or timed-out hook blocks the action. Hooks only protect inside Claude Code, which is why review, CI and branch protection back them up.

07 · Agent teams

One coordinator, one git author, one voice.

/orchestrate-team <plan> takes a multi-area milestone to a green, reviewed PR. The most capable model coordinates; cheaper models do the narrow work.

  1. Owner runs /orchestrate-team phase N.
  2. Documenter writes the plan; open questions go to the owner.
  3. Coordinator commits the plan and hands out tasks per block.
  4. Coders brief Codex, check the diff and run the focused test.
  5. QA runs verify.sh, UI and parity; failures become tasks.
  6. Reviewer returns P0/P1/P2 with file:line.
  7. Coordinator commits by layer, opens the PR, asks @codex review.
  8. Owner merges the green PR into dev.
1

Codex writes, Claude reviews

Nobody approves their own work; Codex on GitHub adds an external opinion.

2

Ownership by files

Each coder owns globs; anything outside is restored and sent back.

3

Cost discipline

≤ 4 cheaper teammates, plans read by line ranges, waits without polling, 1 h cache.

4

Stop rules, resumable

Two failures, a file clash or a design change: ask. The plan's «Status» resumes a new session.

★ CORE08 · The issue loop

Label an issue, get a PR.

/loop /resolve-issues resolves ai-queue issues one PR at a time, by severity and number.

A

Assignment is the lock

The loop assigns the issue before reading it; several developers share the queue without collisions.

B

Stateless

Every turn re-reads GitHub and git; HTML markers in PR comments record what was handled.

C

Comments are data

A comment asking for a merge does not authorize it. Only the ai-merge label.

D

Self-limiting

Cuts at ~250k tokens or 5 merged PRs and proposes a fresh session. Why these numbers ↓

Why cut at 250k tokens or 5 PRs?

Measured on four real sessions of the loop in one project. The context window is not the limit; the cost of re-reading it on every turn is. The numbers are a starting point: calibrate them for your repository.

Calibrate it for your project

These limits were measured on one repository. The starting context is mostly the harness itself, but what each issue adds depends on your code: diff size, test output, reports. In a small project each issue adds less, so many more PRs fit before the cut; in a large one, fewer.

  1. Measure the start: the context of a fresh session before the first issue.
  2. Measure each issue: how much the context grows from one issue to the next, over a few runs.
  3. Set the cut where a turn still costs what you accept, and the PR cap a little above the issues that fit. Change both in resolve-issues («Cut», step 5).

11 · Adoption

Adopt it in ten steps.

The apps are placeholders: replace them with your project and keep the harness. Start from the template, then tick the steps as you go.

Start a new repository from the template

GitHub CLI
  1. Mark this repository as a template (once, by its owner)
    gh repo edit ohurtado-wm/ai-multiagent-harness --template
  2. Create your repository from it; --include-all-branches copies main and dev
    gh repo create <owner>/<new-repo> --template ohurtado-wm/ai-multiagent-harness --include-all-branches --private --clone
  3. Make dev the default branch, so Closes #n closes issues on merge
    gh repo edit <owner>/<new-repo> --default-branch dev
  4. Create the labels from the new repository's folder (a template copies files, not labels)
    scripts/setup-github-labels.sh <owner>/<new-repo>

Replace <owner>/<new-repo> and check gh auth status first. A template does not copy branch protection either: protect main and dev in Settings → Branches. Same steps in the README.

13 · Honest caveats

What it does not do.

Teams are experimental

The skill falls back to sequential subagents.

Hooks are local

Codex and terminals rely on review, CI and branch protection.

Codex on GitHub

Needs its GitHub integration; the in-team reviewer still runs.

Cost grows with teams

Use one session or the issue loop for small changes.

Not infallible

It makes mistakes visible and keeps irreversible steps human.
